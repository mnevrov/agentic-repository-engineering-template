# Процесс проверки кода

## Зачем независимая проверка

Агент, который написал изменение, склонен повторять собственные допущения. Поэтому self-review полезен, но не равен независимой проверке.

## Уровни риска

### A — обычный

Примеры: локальная бизнес-логика, UI, документация, небольшой рефакторинг.

Требуется:

- тесты;
- self-review;
- обычный независимый review.

### B — повышенный

Примеры: API-контракты, внешние интеграции, конкурентность, миграции, важные данные, производительность.

Дополнительно:

- проверка негативных сценариев;
- совместимость/rollback;
- интеграционный тест;
- reviewer должен искать скрытые предположения.

### C — критический

Примеры: authentication/authorization, секреты, destructive operations, финансовая логика, права доступа, криптография.

Дополнительно:

- атакующая независимая проверка;
- явная модель угроз для изменения;
- проверка fail-closed поведения;
- повторные раунды до отсутствия открытых P0/P1;
- при возможности — второй человек для финального решения.

## Severity

- **P0** — критическая уязвимость / потеря данных / системный отказ.
- **P1** — серьёзный дефект, блокирующий принятие.
- **P2** — существенное улучшение, которое можно принять осознанно.
- **P3** — косметика/поддерживаемость.

## Clean-context review

Независимому reviewer передайте:

- задачу и AC;
- архитектурные инварианты;
- diff;
- результаты тестов.

Не передавайте длинное самооправдание автора изменения до первой оценки.
