# Процесс проверки кода

## Зачем независимая проверка

Агент, который написал изменение, склонен повторять собственные допущения. Поэтому self-review полезен, но не равен независимой проверке. Для завершённой задачи independent review обязателен; отсутствие доступного reviewer означает `partial`, а не `passed`.

## Уровни риска

### A — обычный

Примеры: локальная бизнес-логика, UI, документация, небольшой рефакторинг.

Требуется:

- тесты или иной воспроизводимый acceptance signal;
- self-review;
- один независимый clean-context review;
- P0 блокирует завершение.

### B — повышенный

Примеры: API-контракты, внешние интеграции, конкурентность, миграции, важные данные, производительность.

Дополнительно:

- проверка негативных сценариев;
- совместимость/rollback;
- интеграционный тест, если применим;
- reviewer должен искать скрытые предположения;
- P0/P1 блокируют завершение.

### C — критический

Примеры: authentication/authorization, секреты, destructive operations, финансовая логика, права доступа, криптография.

Дополнительно:

- атакующая независимая проверка;
- явная модель угроз для изменения;
- проверка fail-closed поведения;
- повторные раунды до отсутствия открытых P0/P1;
- при возможности — второй человек для финального решения.

## Severity

- **P0** — критическая уязвимость / потеря данных / системный отказ.
- **P1** — серьёзный дефект, блокирующий принятие.
- **P2** — существенное улучшение, которое можно принять осознанно.
- **P3** — косметика/поддерживаемость.

## Clean-context review

Независимому reviewer передайте:

- задачу и AC;
- архитектурные инварианты и релевантные ADR;
- diff;
- результаты реально выполненных тестов/проверок.

До первой оценки не передавайте историю реализации, длинное самооправдание автора или перечень отвергнутых им альтернатив.

## Review artifact

Reviewer сохраняет результат в `docs/reviews/<TASK-ID>-review.md` (можно использовать `.ai/templates/REVIEW.md`). Артефакт должен содержать:

- reviewer/model/session identity, если она известна;
- входной scope и SHA/diff reference;
- P0/P1/P2/P3 findings;
- проверку AC и evidence claims;
- итог `approved`, `changes_required` или `blocked`;
- оставшиеся риски.

Review, выполненный тем же контекстом, который писал код, считается self-review и не заменяет independent review.

## Явное исключение из review-gate

Independent review является нормальным обязательным путём, но процесс должен уметь честно описать исключительную ситуацию, когда ответственный человек сознательно принимает изменение без завершённого независимого review.

Такое решение **не превращает отсутствующий review в `approved`**.

Допустимый порядок:

1. Ответственный человек явно пишет в Task или PR, что review-gate пропускается как исключение.
2. Указывается причина: например, недоступность reviewer, срочное operational решение или сознательное принятие риска.
3. В Task поле independent review помечается `waived`/`not completed`, а не `approved`.
4. Telemetry попытки остаётся `partial`, если обязательный independent review фактически не выполнен.
5. В PR/commit evidence указывается остаточный риск и решение человека.
6. При необходимости создаётся follow-up Task на последующую проверку.

Обычная невозможность дождаться ответа AI-reviewer сама по себе не является доказательством корректности изменения.

Для задач уровня C review-gate не следует обходить как обычную практику. Если экстренная эксплуатационная процедура требует исключения, она должна регулироваться отдельной incident/emergency policy проекта и оставлять явный audit trail.
