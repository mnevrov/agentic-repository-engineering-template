# Цикл разработки

## Принцип

Один цикл должен давать один проверяемый результат и не тащить за собой несвязанный рефакторинг.

## 0. Восстановить контекст

Прочитать:

1. `docs/INDEX.md`
2. ROADMAP / TODO
3. релевантную архитектуру и ADR
4. файл задачи

## 1. Выбрать одну задачу

Хорошая задача:

- имеет ID;
- помещается в один разумный цикл;
- имеет критерии приёмки;
- имеет понятный способ проверки;
- указывает риск A/B/C и режим human gate.

Если это не так — сначала декомпозировать.

## 2. Зафиксировать критерии приёмки

До реализации должно быть понятно, какие наблюдаемые признаки означают успех.

## 3. Оценить риск

- A — обычный;
- B — повышенный;
- C — критический.

См. `code-review.md`.

## 4. Подтверждение человеком

До реализации показать задачу, AC, затрагиваемые компоненты, риск, план и способ проверки.

- **B/C:** явное подтверждение человека обязательно.
- **A:** подтверждение обязательно по умолчанию; его можно заранее делегировать только явной записью `Human gate: delegated` в файле задачи.
- **Опасные/необратимые действия:** отдельное подтверждение обязательно независимо от уровня риска.

Без требуемого gate к реализации не переходить.

## 5. Сначала проверяемость

Предпочтительно:

```text
критерий → тест/сценарий → ожидаемое падение → реализация → прохождение
```

Если TDD неприменим, заранее определить иной воспроизводимый сигнал успеха.

## 6. Минимальная реализация

Не расширять объём задачи. Обнаруженные соседние проблемы — в TODO.

## 7. Локальные проверки

Запустить соответствующие команды из `Makefile` и записать реальные результаты. `NOT CONFIGURED` — отдельное состояние и не является PASS.

## 8. Самопроверка

Проверить diff как reviewer:

- нет ли лишних изменений;
- соблюдены ли инварианты;
- покрыты ли негативные сценарии;
- не ослаблены ли тесты;
- не попали ли секреты;
- обновлена ли документация.

## 9. Независимая проверка

Обязательна для завершённой задачи. Использовать другой агент/модель или новую сессию без истории реализации. Reviewer получает только задачу/AC, инварианты и ADR, diff и фактические результаты проверок.

Результат сохраняется отдельным артефактом `docs/reviews/<TASK-ID>-review.md`. Если независимый review недоступен, цикл фиксируется как `partial`/`failed`, но не `passed`.

## 10. Доказательства

Собрать evidence summary согласно `evidence-ladder.md`. Уровень доказательства определяется реально выполненными проверками, а не формулировкой отчёта.

## 11. Definition of Done

Проверить `definition-of-done.md`.

## 12. Обновить память и трассируемость проекта

Задача, TODO, ROADMAP, ADR, архитектура — всё должно отражать состояние после изменения. Проверить минимальную цепочку `task → evidence → review → commit`; для крупных проектов при необходимости использовать полную цепочку из `traceability.md`.

## 13. Записать телеметрию цикла

Каждая попытка должна оставить запись в `.ai/telemetry/cycles.jsonl`, включая `failed`, `partial` и `aborted`.

Использовать `scripts/record-cycle.py`. Минимум вводится вручную: `task_id`, начало, окончание и результат. Скрипт автоматически добавляет доступные Git/duration evidence (`duration_seconds`, `git_head`, состояние worktree, изменённые файлы и размер tracked diff). Остальные метрики передавать только если они реально известны.

См. `telemetry.md`.

## 14. Коммит

Один завершённый цикл — один осмысленный коммит или максимально близкая к этому структура истории. Из сообщения или связанной задачи должно быть понятно, какой Task закрывает изменение.
