# Цикл разработки

## Принцип

Один цикл должен давать один проверяемый результат и не тащить за собой несвязанный рефакторинг.

## 0. Восстановить контекст

Прочитать:

1. `docs/INDEX.md`
2. ROADMAP / TODO
3. релевантную архитектуру и ADR
4. файл задачи

## 1. Выбрать одну задачу

Хорошая задача:

- имеет ID;
- помещается в один разумный цикл;
- имеет критерии приёмки;
- имеет понятный способ проверки.

Если это не так — сначала декомпозировать.

## 2. Зафиксировать критерии приёмки

До реализации должно быть понятно, какие наблюдаемые признаки означают успех.

## 3. Оценить риск

- A — обычный;
- B — повышенный;
- C — критический.

См. `code-review.md`.

## 4. Подтверждение человеком

До существенной реализации показать план. Человек проверяет направление, а не каждую строку кода.

## 5. Сначала проверяемость

Предпочтительно:

```text
критерий → тест/сценарий → ожидаемое падение → реализация → прохождение
```

Если TDD неприменим, заранее определить иной воспроизводимый сигнал успеха.

## 6. Минимальная реализация

Не расширять объём задачи. Обнаруженные соседние проблемы — в TODO.

## 7. Локальные проверки

Запустить соответствующие команды из `Makefile` и записать реальные результаты.

## 8. Самопроверка

Проверить diff как reviewer:

- нет ли лишних изменений;
- соблюдены ли инварианты;
- покрыты ли негативные сценарии;
- не ослаблены ли тесты;
- не попали ли секреты;
- обновлена ли документация.

## 9. Независимая проверка

По возможности использовать другой агент/модель или новую сессию без истории реализации.

## 10. Доказательства

Собрать evidence summary согласно `evidence-ladder.md`.

## 11. Definition of Done

Проверить `definition-of-done.md`.

## 12. Обновить память проекта

Задача, TODO, ROADMAP, ADR, архитектура — всё должно отражать состояние после изменения.

## 13. Коммит

Один завершённый цикл — один осмысленный коммит или максимально близкая к этому структура истории.
