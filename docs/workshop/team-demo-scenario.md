# Сценарий командной демонстрации: 15 минут

Цель демонстрации — показать не «как AI быстро пишет код», а **как репозиторий удерживает контекст, ограничивает работу агента, заставляет получать проверяемый результат и сохраняет историю нескольких итераций**.

Для демонстрации используется небольшой проект **Mini Task Board** — локальный веб‑трекер задач на Python 3 без внешних зависимостей. Итог каждой итерации виден в браузере, а инженерная часть — в Task, тестах, review, evidence и telemetry.

Подробная спецификация проекта и итераций: [`demo-project.md`](demo-project.md).

---

## Что аудитория должна увидеть

За одну короткую демонстрацию команда должна успеть увидеть пять вещей:

1. новый агент восстанавливает контекст из репозитория без длинного вводного промта;
2. работа ограничена одной Task и измеримыми Acceptance Criteria;
3. агент останавливается на human gate там, где это требуется;
4. «готово» подтверждается тестами/review/evidence, а не сообщением модели;
5. после нескольких итераций остаётся работающий продукт и воспроизводимая история в Git.

Финальный визуальный результат:

```text
Mini Task Board

Открыто: 2   Выполнено: 1

[Высокий] Подготовить демонстрацию       [Выполнить]
[Средний] Проверить CI                    [Выполнить]
[Низкий]  Обновить README                 ✓

+ Новая задача
```

Приложение открывается локально в браузере, например на `http://127.0.0.1:8000`.

---

# Подготовка до выступления

Не стоит строить весь проект в live‑режиме. Время ответа модели, сеть и внешний provider непредсказуемы.

Подготовьте отдельный демонстрационный репозиторий, созданный из этого template, например:

```text
agentic-template-demo
```

В нём должны быть заранее сохранены checkpoints:

```text
demo/00-bootstrap
demo/01-read-board
demo/02-create-task
demo/03-persistence
demo/04-finished
```

Это могут быть Git tags или branches.

На выступлении **одну итерацию желательно провести действительно live**, а остальные показать переключением между checkpoints. Тогда демонстрация одновременно честная и надёжная.

Перед началом:

```bash
git status
./scripts/repo-doctor
make test-template
make check
make test
```

Все команды должны быть зелёными в подготовленном demo repository.

Также заранее запустите браузер и терминал крупным шрифтом.

# Рекомендуемый тайминг

## 0:00–1:30 — проблема

Покажите пустой новый чат coding agent и репозиторий.

Короткий тезис:

> Обычно знания о проекте остаются в чате: что уже решили, что запрещено менять, какая задача следующая и чем её проверять. Здесь долговременная память находится в Git, поэтому можно сменить модель или начать новую сессию без ручного восстановления контекста.

Откройте:

- `AGENTS.md`;
- `docs/INDEX.md`;
- `docs/architecture/overview.md`;
- `docs/backlog/TODO.md`.

Не читайте документы целиком. Покажите только, что контекст структурирован и находится рядом с кодом.

---

## 1:30–3:00 — Task вместо большого промта

Откройте `docs/tasks/DEMO-1.md`.

Покажите четыре поля:

- scope;
- Acceptance Criteria;
- risk;
- verification/evidence.

Ключевой тезис:

> Агент получает не просьбу «сделай приложение», а одну небольшую проверяемую инженерную задачу.

Покажите backlog:

```text
DEMO-1 — показать список задач
DEMO-2 — добавить создание задачи
DEMO-3 — сохранить задачи между перезапусками
DEMO-4 — добавить фильтр и счётчики
```

---

## 3:00–7:00 — одна реальная live‑итерация

Лучше всего проводить live **DEMO-2 — создание задачи**, потому что изменение небольшое, визуально заметное и содержит негативный сценарий проверки.

Начните новую сессию OpenCode/Codex CLI/Claude Code из корня demo repository.

Минимальный prompt:

```text
Следуй AGENTS.md. Выполни следующую готовую задачу из TODO. Сначала покажи выбранную Task, риск, Acceptance Criteria, план и способ проверки. Не выходи за scope задачи.
```

Что важно показать аудитории:

### 1. Агент сам читает repository context

Не пересказывайте ему архитектуру вручную.

### 2. Агент называет одну Task

Ожидаемо:

```text
DEMO-2 — добавить создание задачи
```

### 3. Он формулирует план до изменения кода

Ожидаемые пункты:

- POST/form handler;
- валидация пустого имени;
- тест успешного создания;
- тест invalid input;
- минимальное изменение UI.

### 4. Human gate

Для demo TASK можно использовать risk B, потому что появляется write‑операция и контракт изменения состояния.

На экране должно быть видно, что реализация не начинается молча.

Подтвердите коротко:

```text
План подтверждаю. Выполняй только DEMO-2.
```

### 5. Проверки

После реализации покажите реальные команды:

```bash
make check
make test
```

Если агент запускает их сам — лучше оставить вывод видимым.

### 6. Визуальный результат

Обновите браузер и создайте задачу:

```text
Подготовить демонстрацию
```

Затем специально попробуйте отправить пустое название и покажите, что оно отклоняется.

Ключевой тезис:

> Мы увидели не только генерацию кода. Мы увидели границу задачи, human gate, положительный и отрицательный acceptance‑сценарий и работающий результат.

---

## 7:00–9:00 — новая сессия, контекст не потерян

Это один из самых важных моментов демонстрации.

Закройте текущую сессию агента или откройте новую.

Переключитесь на checkpoint после DEMO-2, если live‑итерация не была сохранена.

Дайте новому агенту только:

```text
Изучи репозиторий и скажи: что уже реализовано, какая следующая готовая задача и чем она должна быть проверена. Код пока не меняй.
```

Ожидаемый ответ:

- DEMO-1 и DEMO-2 завершены;
- следующая — DEMO-3;
- нужна persistence/restart проверка;
- risk B из-за данных;
- применимые архитектурные ограничения перечислены из repo docs.

Ключевой тезис:

> Это новая сессия, но состояние проекта не пришлось восстанавливать из старого чата.

---

## 9:00–11:30 — показать ещё две итерации через Git

Не выполняйте их live. Покажите историю:

```bash
git log --oneline --decorate --max-count=8
```

Пример:

```text
8e21... DEMO-4 add task filters and counters
61fa... DEMO-3 persist tasks atomically
42b7... DEMO-2 add validated task creation
17ac... DEMO-1 render task board
0a91... bootstrap demo project
```

Переключитесь на `demo/03-persistence` или покажите diff DEMO-3.

### DEMO-3

Покажите:

1. создать задачу в браузере;
2. остановить процесс;
3. снова запустить;
4. задача осталась.

Это хороший пример задачи повышенного риска: работа с данными требует более сильных доказательств, чем простое изменение UI.

Затем переключитесь на финальный checkpoint `demo/04-finished`.

### DEMO-4

Покажите итог:

- фильтр открытых/завершённых задач;
- счётчики;
- изменение статуса задачи;
- аккуратный UI.

---

## 11:30–13:00 — review и evidence

Откройте один review artifact:

```text
docs/reviews/DEMO-3-review.md
```

Покажите:

- проверенный SHA/diff;
- findings P0/P1/P2/P3;
- verdict;
- остаточный риск.

Затем Task:

```text
docs/tasks/DEMO-3.md
```

и раздел `Доказательства`.

Ключевой тезис:

> Автор модели и reviewer — разные роли. Сообщение «я всё проверил» от агента не является independent review.

Не надо подробно разбирать severity — достаточно показать, что проверка сохраняется как отдельный воспроизводимый артефакт.

---

## 13:00–14:00 — измеримость

Покажите:

```bash
make telemetry-check
make telemetry-summary
```

И последние записи:

```bash
tail -4 .ai/telemetry/cycles.jsonl
```

Обратите внимание на:

- task ID;
- длительность;
- модель/provider, если доступны;
- review rounds;
- result;
- evidence reference.

Ключевой тезис:

> Через несколько недель можно обсуждать agentic development не по ощущениям, а по lead time, rework, review findings, стоимости и человеческому времени.

---

## 14:00–15:00 — итог

Покажите одновременно браузер и короткую Git‑историю.

Финальная формулировка:

> За несколько итераций получился небольшой работающий продукт. Но главная демонстрация не сам Task Board. Главное — любой новый агент может понять состояние проекта, взять одну следующую задачу, пройти заданные проверки и оставить после себя доказуемый инженерный результат. Модель можно заменить, репозиторий остаётся источником истины.

После этого откройте `README.md` исходного template repository и покажите, что команда может начать с готового onboarding.

# План B при проблемах с моделью или сетью

Если provider отвечает медленно или coding agent недоступен:

1. покажите уже сохранённый план агента для DEMO-2;
2. переключитесь на `demo/02-create-task`;
3. запустите `make test`;
4. покажите результат в браузере;
5. продолжите сценарий как обычно.

Не имитируйте live‑работу. Скажите прямо, что переключились на заранее сохранённый checkpoint для экономии времени.

Ценность демонстрации от этого не теряется: предмет презентации — воспроизводимый repository workflow, а не latency конкретной модели.

---

# Что не стоит показывать

Для короткого выступления не нужно:

- подробно читать весь `AGENTS.md`;
- объяснять JSON Schema telemetry;
- демонстрировать установку OpenCode/Codex/Claude;
- проводить live adversarial review;
- выбирать модель по benchmark;
- показывать большой реальный корпоративный репозиторий;
- давать агенту расплывчатую задачу «сделай всё приложение».

Это размывает основную мысль.

---

# Критерий успешной демонстрации

После выступления участник команды должен уметь сформулировать примерно следующее:

> «Шаблон не заменяет coding agent. Он хранит инженерный контекст и задаёт повторяемый цикл: одна Task → human gate → реализация → реальные проверки → независимый review → evidence/telemetry → commit. Поэтому можно безопаснее менять модели и продолжать работу между сессиями».
